# Work Hour Pace Calculator

## User-visible outcome

사용자가 이번 정산기간의 정상근무시간(목표)과 현재까지의 누적근무시간을 입력하고, 앞으로 일할 계획을 "예상 근무 계획"(시간·분·일수 단위 항목 여러 개)으로 입력하면, 그 계획대로 일했을 때 정상근무시간을 초과하는지·정확히 충족하는지·부족한지를 즉시 계산해서 알려준다. 입력한 예상 근무 계획은 저장되어, 다음에 웹페이지를 열었을 때도 그대로 남아 있다.

## Scope

- 포함:
  - 정상근무시간·누적근무시간 수동 입력 (기존과 동일)
  - "예상 근무 계획" 여러 항목(시간·분·일수) 입력, 추가·삭제
  - 계획 항목들의 합계를 반영한 결과(초과 예상/충족 예상/부족 예상) 계산과 표시
  - 예상 근무 계획 항목의 브라우저 저장(localStorage) 및 재방문 시 자동 복원
- 제외: 근태 화면 캡처 업로드·자동 숫자 인식, attendance.lge.com 자동 연동, 로그인/인증, 서버 측 데이터 저장. 이 결과 이후 실제 근태 화면 예시를 확보하면 별도 스펙에서 다룬다.
- 대체됨: 남은근무일수를 단일 숫자로 직접 입력하던 기존 방식과, 이에 기반한 "정상 진행 중"/"부족 위험"(하루 평균 추천) 판정은 예상 근무 계획 기반의 직접 판정으로 대체되어 더 이상 제공하지 않는다.

## Inputs

- 정상근무시간: 이번 정산기간의 목표 총 근무시간 (시간, 소수점 허용, 0 이상, 저장하지 않음)
- 누적근무시간: 현재까지 실제로 일한 시간 (시간, 소수점 허용, 0 이상, 저장하지 않음)
- 예상 근무 계획: 0개 이상의 항목 목록. 각 항목은 시간(정수, 0 이상) · 분(정수, 0 이상) · 일수(정수, 0 이상)로 구성되며, "이 시간만큼 일하는 날이 이 일수만큼 있다"를 의미한다. "+ 추가"로 항목을 늘리고 각 항목을 개별적으로 삭제할 수 있다. 브라우저에 저장되어 재방문 시 그대로 복원된다.

정상근무시간·누적근무시간은 사용자가 근태 화면에서 직접 읽어 매번 입력한다. 정산기간의 날짜 범위나 공휴일·개인 휴가 계산은 이 결과에서 다루지 않는다.

## Calculation and judgment

- 총예상근무시간 = Σ (항목.시간 + 항목.분 ÷ 60) × 항목.일수 (모든 예상 근무 계획 항목 합계)
- 예상누적근무시간 = 누적근무시간 + 총예상근무시간
- 판정:
  - 예상누적근무시간 > 정상근무시간 → **초과 예상** (초과시간 = 예상누적근무시간 − 정상근무시간)
  - 예상누적근무시간 = 정상근무시간 → **충족 예상**
  - 예상누적근무시간 < 정상근무시간 → **부족 예상** (부족시간 = 정상근무시간 − 예상누적근무시간)

## Acceptance criteria

- "+ 추가"를 누르면 시간·분·일수를 입력할 수 있는 예상 근무 계획 항목이 새로 나타난다.
- 예상 근무 계획 항목이 여러 개일 때 각 항목을 개별적으로 삭제할 수 있다.
- 정상근무시간·누적근무시간·예상 근무 계획을 입력하고 계산을 실행하면 총예상근무시간과 판정 결과(초과 예상/충족 예상/부족 예상 중 하나)가 화면에 표시된다.
- 예상누적근무시간이 정상근무시간보다 크면 "초과 예상" 판정과 초과 시간이 표시된다.
- 예상누적근무시간이 정상근무시간과 같으면 "충족 예상" 판정이 표시된다.
- 예상누적근무시간이 정상근무시간보다 작으면 "부족 예상" 판정과 부족 시간이 표시된다.
- 정상근무시간·누적근무시간, 또는 예상 근무 계획 항목의 시간·분·일수 중 하나라도 음수이거나 빈 값이면 계산 대신 오류 메시지가 표시된다.
- 예상 근무 계획 항목을 추가·수정·삭제한 뒤 웹페이지를 다시 불러오면, 마지막으로 남아 있던 항목들이 그대로 복원되어 채워져 있다.
- 정상근무시간·누적근무시간은 저장되지 않으며, 웹페이지를 다시 불러오면 빈 값으로 시작한다.

## Settled constraints and rationale

- 남은근무일수 단일 숫자 대신 예상 근무 계획(여러 항목)을 쓰는 이유: 사용자가 실제로 어떻게 일할지 시간·분 단위로 구체적으로 계획하면, "하루 평균 얼마나 일해야 하는지" 추천하는 것보다 그 계획이 목표를 채우는지 직접 판정하는 것이 더 정확하고, 남은근무일수를 별도 숫자로 또 입력할 때 생기는 불일치 위험도 없앤다. (이번 세션에서 사용자가 "대체로 진행"을 직접 확정함.)
- "정상 진행 중"/"부족 위험"(하루 8시간 기준 추천) 판정을 없앤 이유: 사용자가 이미 구체적 계획을 입력하므로, 일반적인 하루 평균 추천치 대신 그 계획의 실제 결과(초과/충족/부족 예상)를 바로 보여주는 것이 더 유용하다.
- 예상 근무 계획만 저장하고 정상근무시간·누적근무시간은 저장하지 않는 이유: 요청 범위가 "예상 근무시간" 저장이었고, 나머지 두 값은 매번 근태 화면에서 새로 확인해 입력하는 값이라 저장 대상에서 제외했다.
- 정산기간의 날짜·공휴일·개인 휴가를 앱이 스스로 계산하지 않는 이유: 사용자가 근태 화면에서 이미 계산된 값(정상근무시간, 누적근무시간)을 직접 읽어 입력하므로, 앱이 별도의 캘린더/공휴일 로직을 가질 필요가 없다.
- 로그인/서버 저장을 다루지 않는 이유: PRODUCT.md에도 인증 방식은 Unknown으로 남아 있고, 이번 범위는 브라우저 로컬 저장으로 충분하다.

## Assumptions

- 분(分) 값이 59를 넘어도(예: 90분) 시간으로 환산해 계산한다(90분 = 1.5시간); 별도 범위 제한은 두지 않는다.
- 저장은 브라우저의 localStorage를 사용하며, 로그인·계정 없이 이 브라우저에만 남는다. 프라이빗 모드 등 localStorage를 사용할 수 없는 환경은 다루지 않는다.
- 예상 근무 계획 항목이 하나도 없어도(빈 목록) 계산은 가능하며, 이 경우 총예상근무시간은 0으로 취급한다.
- 근무일수는 정수, 근무시간(정상근무시간·누적근무시간)은 소수점을 허용한다.

## Off-limits (excluded, with reason)

- 근태 화면 캡처 업로드·자동 숫자 인식: 실제 화면 예시 부재로 지금 구현하면 잘못된 가정에 기반하게 될 위험이 크다. 실제 화면 확보 후 별도 스펙에서 다룬다.
- attendance.lge.com 자동 접속·연동: 같은 이유로 제외. PRODUCT.md의 향후 확장 계획으로 남겨둔다.
- 로그인/인증, 서버 측 사용자별 데이터 저장: 이번 결과 검증에 불필요하다.

## Deferred points

- 캡처 화면 인식 항목·레이아웃 확정 (실제 화면 예시 확보 후)
- attendance.lge.com 자동 연동 방식
- 전 직원 대상 서비스로서의 인증·서버 측 개인별 데이터 보관 방식

## Remaining risks

- 예상 근무 계획은 어디까지나 "계획"이며, 실제로 그 시간만큼 일했는지는 이 도구가 검증하지 않는다.
- 브라우저의 localStorage가 지워지거나(캐시 삭제 등) 다른 브라우저/기기로 접속하면 저장된 예상 근무 계획이 보이지 않는다.
- 세 입력값(정상근무시간·누적근무시간·예상 근무 계획)이 실제 근태 화면의 어떤 항목과 정확히 대응하는지 아직 실제 화면으로 검증되지 않았다.
